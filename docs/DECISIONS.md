| 2026-10-24 | Every test that uses the network does so on ports of its own process, claimed through a numbered slot locked in a file ([RUNNING.md](RUNNING.md), *Ports of their own*); the exchange and the trading client gain options for their ports and groups, the book's by default. Chosen over a lock for the whole machine (which would block the tests while a debug session is open) and a better guard (which turns interference into failure without preventing it). Found first: the back end's system test, run while a replay published on the book's stream as VS Code's lockstep session does, passed on the replay's market data, all 200 updates it checked, without checking its own exchange. |

Runner time is free for a public repository on standard runners (GitHub's billing documentation), and the Free plan runs 20 jobs at once. |
| 2026-10-24 | The market data stays on the machine: the exchange sends its multicast on the loopback interface, the one its code already names, and every listener, the trading client and the viewer included, joins there. Chosen over a time-to-live of 0 on the default interface (one change, in the senders only), which keeps the data on the machine but still needs a network to send or join, and announces each listener's membership on it. Measured first: today every update went out on the Wi-Fi; multicast over loopback works without root, although TECH-DEBT said it needed it. |
| 2026-10-24 | The book's `ASSERT` becomes a macro that evaluates its message only when the check fails, rather than each hot-path call being rewritten as an `if` around `FATAL`: one change fixes every call, and any written later; every call compiles unchanged. A test program that counts allocations checks the hot paths, and the queue's full check is an `ASSERT` again, like the rest of the file. |
| 2026-10-24 | A write to a full lock-free queue stops the program ("LFQueue full"), rather than overwriting the oldest unread message (as the book's queue did, silently: an overwritten market update leaves no gap in the sequence numbers) or making the writer wait (which changes the latency the book measures, and can hang the order server and the matcher on each other's full queues). It costs one comparison per write. The logger's queues are the same queue, so a logger 8,388,608 values behind (each character of a message is one, and each number) stops the program too. |
| 2026-10-24 | A recording that can't be written stops, says so on stderr, and the exchange runs on, as before: the recording is for studying a run, and what it holds is exact as far as it goes. A write cut off part-way, which made the whole recording unreadable, is now cut back to the last whole request. Rejected: stopping the exchange, which ends the trading for a problem with a diagnostic; a marker in or beside the file, which a full disk, the usual cause, can't write either. |
| 2026-10-24 | The exchange refuses a request its matcher can't process (TECH-DEBT's item 5 of the third sweep), in the order server as it arrives: a new order with a new response, `REJECTED`, a cancel with `CANCEL_REJECTED`; a client id past the exchange's tables is dropped and logged, since it can't be answered. The book's client marks a rejected order dead. Rejected: skipping such a request, which would leave the client believing its order exists, and keeping the book's behaviour, in which one request ends the exchange. The limit of 1,048,576 order ids per client stays, to be raised only if it becomes a problem. |
